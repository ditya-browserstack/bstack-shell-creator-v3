Design tooling · adoption guide

Keep your design shell honest about production

A design shell drifts the moment it ships. shell-sync reads what actually merged, checks it against your shell, and codes in what is missing — stopping for your approval first. It also gives you named versions to explore ideas in, which keep up with production on their own, and turns any of them into one file a developer can open.

Needsa Claude Design shell
To adoptan interview + a screen map

The problem

Shells rot quietly

Most teams end up with a standalone HTML shell of their product: a clickable mirror you can open without a login, a device or a test run. It is the artefact designers reason with and developers glance at.

Then it drifts. Features ship and the shell does not move. Someone mocks an idea directly in it. Six weeks later nobody can tell which parts are real, so nobody trusts any of it, and it quietly stops being used.

Both halves of that are fixable. Keep one shell rigorously equal to production, and put every unreleased idea somewhere else that is clearly labelled.

What it does

Three things, and only one is the weekly job

The hard part, solved

Most of what ships is invisible

The naive version of this tool floods you with noise. In one real two-week window a product merged well over a hundred changes; after dropping version bumps, lockfiles and other teams' work in a shared monorepo, eight candidates remained. Asking the tracker what each one actually was cut it to one.

The rest were backend validators, analytics properties, worker tuning, an auth migration — real work, invisible in a design shell. That cut cannot be scripted: it needs the ticket read. It is the difference between a gap report you act on and one you learn to ignore.

Versions

One shell everyone trusts, plus your own

The shared shell holds only what shipped. Anything unreleased forks off it as a named version, yours to change.

Versions do not go stale. Each sync merges production back into every one of them: the new production work arrives, your own design edits stay exactly as you left them. When both sides changed the same region the merge stops and the version is left untouched, and you are told which two disagree. That refusal is the only reason merging automatically is safe — without it, the choice is between rotting versions and silently mangled ones.

A version is invisible until you publish it, and an unpublished one looks identical to a shared one, so every listing marks each shared or ONLY ON THIS MACHINE. Publishing is one command; forgetting it is the easiest way to think your team can see something they cannot.

Each version is a git branch rather than a copy of the shell, so nothing new appears in your repository’s folders and ten variations do not cost ten times the space. Only the app source is versioned: the embedded fonts are almost all of a shell’s size, never vary, and are recombined only when a file is produced. Fork points, drift and history all come from git rather than from a note the tool keeps, which is what stops them disagreeing with what actually happened.

Adopting it

What it takes to point this at your product

Nothing in the machinery knows which product it is looking at. Taking an export apart, reading its surface, matching what shipped, versioning, capture — all of it is generic. Only the answers differ.

StepWhat is involved
PrerequisiteYou need a Claude Design shell of your product. One bundled HTML export. Without it there is nothing to keep honest.
InstallUnzip the folder, run one script, restart. About two minutes, and no repository access to arrange.
Onboard/shell-sync onboard interviews you: ticket prefix, repos, which branch production ships from. It checks each repo is reachable and warns about the answers that fail silently.
Screen mapOne entry per screen. The only manual part — see below.

The screen map, in full

Each screen needs an entry saying how to reach it and how to know you arrived. That is what lets the tool photograph your screens reliably rather than whatever happened to be open: 

slug:    test-suites
nav:     ["Test suites"]          what to click to get there
gate:    suitesOpen               the internal state that shows this screen
verify:  "Create test suite"      text proving you landed in the right place

Claude reads your shell, finds the states and drafts the entries; you confirm them. How many you need depends on how many screens you want boarded — start with the ones people actually look at and add the rest later. A test then checks every state exists and every verify string really sits inside it — on the first product that test caught two wrong entries before they shipped, one pointing at the wrong state and one with a capitalisation that did not match the shell.

Worth knowing before you commit

Two people editing the shell in the same week will conflict — it is a single large file and git cannot merge it usefully. Everything else merges cleanly. If your team is likely to run this concurrently, agree one owner for the weekly sync; it is a ten-minute job once a week.

The flow you will actually live in

Most weeks you are not syncing. You are checking you are current, trying something, or sending a file to somebody.

What you install

One folder, no repository access

You were sent a shell-sync folder, about 300 KB. That is the whole tool. There is no repository to be added to, no access request, and nothing to wait for. 

unzip shell-sync.zip
bash shell-sync/install.sh     links it into ~/.claude/skills
restart Claude Code, then:
/shell-sync onboard

What arrives is deliberately only the tool. There is no shell in it and no configuration, because those are yours: the onboarding interview writes your profile, and you supply your own Claude Design export. Nothing carries over from whoever sent it to you — not their product, not their screens, not their record of what shipped.

The four you will actually touch

FileWhat it does for you
install.shLinks the folder into ~/.claude/skills/ so the command exists. Checks your Python version and warns if the GitHub CLI is missing. Refuses rather than overwrites if something is already there.
README.mdInstall, prerequisites, and the list of commands. What to read if you have thirty seconds.
SKILL.mdThe full instructions the assistant reads and follows every run. This is the answer to “what exactly is it about to do to my shell?” — including every point where it must stop and ask you.
tests/python3 -m unittest discover -s tests. Worth running once after install: it is the fastest way to know the copy you were sent is intact. Some tests skip on a fresh install because they need a shell and a screen map you do not have yet — that is expected, not a failure.

Inside lib/ — one file per job

You never run these directly; the assistant does. They are listed because the honest answer to “what did you just install?” should be available, and because knowing which file owns which step makes it much easier to say what went wrong when something does.

FileIts one jobWhy it is separate
bundle.py Splits a Claude Design export into fonts and app source, and joins them back. The app source lives inside a <script> tag with escaped slashes. Rejoin it wrongly and the page renders blank with no error at all. One file owns that rule.
harvest.py Asks GitHub which pull requests shipped in the window. Its filters are tuned against real releases — version bumps, lockfiles, unit tests, other teams’ work in a shared repo.
index.py Reads your shell and lists everything it can show: commands, screens, visible labels. This is what “is the feature already here?” is answered against. It handles both export shapes Claude Design produces.
match.py Scores each shipped feature against that list. Present, missing, or unsure. Its job is to refuse to guess: anything it is not confident about comes back as unsure, for the assistant to settle by reading the shell.
capture.mjs Walks your shell in a real browser and screenshots each screen. The only JavaScript file. Browser automation is a Node library, so this one step is not Python.
gitstore.py Reads and writes git branches without ever checking one out. Versions are branches. Checking one out would swap the tool’s own code and its history mid-run, and would fail whenever you had unsaved work — so nothing here ever does.
versions.py Forks a variation, reports how far behind it is, packs one into a sendable file. Also refuses version names that could reach outside their own branch namespace.
storyboard.py Turns captured screens into labelled artboards in Claude Design. Holds the screen map — the one part of setup that is genuinely yours to write.
ledger.py Remembers what was added and when the last run was. This is what makes a missed week catch up rather than silently skip.
paths.py Reads your profile and works out where everything lives. Includes a fifty-line config reader, so there is no dependency to install.
onboard.py Turns your interview answers into a profile — after checking them. Confirms every repo you name is actually reachable, and warns about the answers that fail silently.
doctor.py Reports what your copy has and what is missing. Writes nothing. What /shell-sync check runs. The right first move whenever something looks wrong.
package.py Builds this zip, so you can pass the tool on to someone else. Ships the tool and holds back all content — no shell, no profile, no history. It refuses to build if anything of yours would leak.
If you ever go looking in here

bundle.py and index.py are the two where a freehand rewrite quietly produces a broken shell rather than an error. Everything else fails loudly. It is all standard-library Python — readable, and nothing to install — but those two earned their scars, and the comments in them say what from.

Where your own work goes

Two things the tool produces are yours to keep somewhere: the shell it maintains, and the versions you fork from it. By default both live inside the skill folder, which is fine for one person.

If you want a team to share them, point version_repo at a repository your team already has — any repository, it does not matter which, and onboarding asks for it. Versions are stored there as git branches, so nothing new appears in its folders. A relative path is resolved against the folder holding your checkouts rather than against your home directory, so one committed setting works on everybody’s machine. Hand-edited absolute paths were the earlier design, and meant nobody could open anybody else’s version.

Only the app source of a shell is stored, never whole exports. The embedded fonts are almost all of a shell’s weight and never vary, so they live once and are recombined when a file is produced. That is what keeps a week’s change reviewable as a few lines rather than a megabyte of unreadable data.

Design decisions

Why it is built this way

Three choices shape everything else, and each ruled out something more obvious.

The obvious approachWhy it was not used
Screenshot the product,
diff it against the shell		 This was the original plan. It reports everything as different — different fonts, spacing, seed data, real device screens against placeholders — so it cannot answer “is this feature here?”. Comparing the shell’s own text and structure answers it reliably; screenshots then do the job they are good at, which is showing what to build and confirming the result.
No scripts — let the
assistant do all of it		 Tempting, and wrong for the parts that must give the same answer every week. A filter that drifts run to run is indistinguishable from a real change in what shipped, and you would never catch it. So the deterministic work — taking the export apart, reading its surface, filtering, scoring — is code, and the judgement work stays with the assistant.
Add the usual dependencies
(a YAML parser, a test runner)		 Everything is standard-library Python, which means it runs from an unzipped folder with nothing installed — no virtualenv, no version pinning, no pip install failing on somebody’s machine two months from now. The config reader is fifty lines instead of a dependency, and the tests use the runner already in the language.

The one exception is the screenshot step, which is JavaScript — the browser automation that does that job well is a Node library, and reimplementing it would be far worse than accepting one extra runtime. Everything else is Python, and the split is along that line rather than by preference.

Honest limits

What it will not do

It will not invent an appearance. If it cannot reach a feature in the live product — behind a flag, off-plan, needing a real device session — it says so and asks you for a screenshot rather than guessing. Expect that regularly; it is the design working, not failing.

It will not edit your Claude Design document. The connection is one-way: you export, it consumes. Your design work stays authoritative, and a record of every change it made lets a fresh export be re-patched rather than losing that work.

It will not share a board across accounts. Claude Design boards can only be shared inside a Claude team, so anything going to someone outside it goes as a file.

It will not hand you an unverified file. Every change is rendered in a real browser first — the new element must be present and the page must load without errors. If that fails, the shell is restored and the run stops.
